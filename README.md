StudClubs объединяет в одном месте сведения о студенческих клубах, приём заявок на вступление и учёт состава участников. Система замещает разрозненные бумажные журналы, электронные таблицы и переписку в мессенджерах: обучающийся находит объединение в публичном каталоге и подаёт заявку, руководитель рассматривает обращения и ведёт состав своего клуба, а отдел воспитательной работы управляет реестром объединений, справочниками и отчётностью. Каждое изменение данных фиксируется в неизменяемом журнале аудита, что делает решения о приёме прозрачными и проверяемыми.

## Архитектура

Система построена по клиент-серверной архитектуре: клиент отвечает за представление и ввод, сервер — за данные, правила и безопасность.

```
Браузер — React SPA (CSR), TypeScript strict
   │   HTTPS · JSON · операции с префиксом /api
   │   контракт зафиксирован спецификацией OpenAPI
   ▼
Node.js + Express (TypeScript)
   ├── бизнес-правила и автоматы состояний
   ├── аутентификация и авторизация: RBAC + область видимости
   ├── транзакции БД + журнальная запись в той же транзакции
   ├── производные показатели, отчёты, выгрузки CSV
   └── резервные копии, миграции, фоновая просрочка заявок
   │   Prisma ORM (прослойка между кодом и базой данных)
   ▼
PostgreSQL — единственный экземпляр операционных данных
```

Ключевые принципы:

- **Решающие проверки — только на сервере.** Клиентская валидация по общим схемам Zod служит удобству ввода и средством защиты не является.
- **Контракт прежде кода.** Единый источник истины для обеих частей — машиночитаемая спецификация OpenAPI; изменения — только по согласованию обоих исполнителей с обновлением версии контракта.
- **Общий доменный модуль.** Типы, перечисления состояний и схемы валидации определяются однократно в `shared/` и используются обеими частями; дублирование статусов и правил запрещено.
- **Клиент не хранит операционные данные.** Кэш живёт на время сеанса; в localStorage допускаются только настройки интерфейса (тема, плотность, размер страницы реестров).
- **Сеансы не зависят от памяти процесса.** Подписанный токен с ограниченным сроком действия — перезапуск сервера не разрушает работоспособность.
- **Собранный клиент раздаётся сервером** как статические файлы с возвратом `index.html` для маршрутов приложения.

## Быстрый старт

### Предварительные требования

- Node.js 22 LTS (не ниже 22.12);
- pnpm 10+ (проще всего через Corepack: `corepack enable && corepack prepare pnpm@latest --activate`);
- PostgreSQL (рекомендуется 16+; локальная служба или контейнер Docker);
- Git 2.40+.

### Шаги

1. Клонировать репозиторий и установить зависимости:

```bash
git clone <URL репозитория> studClubs
cd studClubs
pnpm install
```

2. Настроить окружение клиента (значения по умолчанию пригодны для разработки):

```bash
cp client/.env.example client/.env
```

Windows PowerShell: `Copy-Item client/.env.example client/.env`.

3. **(этап 1)** Создать `server/.env` по составу из соглашения о разработке (таблица ниже). Секреты в репозиторий не коммитятся.

4. **(этап 1)** Поднять PostgreSQL и применить миграции — версионные изменения структуры БД:

```bash
# вариант — контейнер Docker (проектное решение):
docker run --name studclubs-db -e POSTGRES_PASSWORD=postgres \
  -e POSTGRES_DB=studclubs -p 5432:5432 -d postgres:16

pnpm --filter ./server exec prisma migrate dev
```

5. **(этап 2)** Загрузить демонстрационный набор — seed, предопределённые синтетические данные для показа без ручного наполнения:

```bash
pnpm --filter ./server run db:seed
```

6. Запустить обе части в режиме разработки (в двух терминалах):

```bash
pnpm dev:client               # Vite, http://localhost:5173
pnpm --filter ./server dev    # API, http://localhost:3000
```

7. **(этап 1)** Проверить работоспособность: открыть `http://localhost:5173` и операцию проверки сервера `GET http://localhost:3000/api/health`.

Демонстрационные учётные записи для каждой роли создаются сид-скриптом; перечень логинов и порядок получения паролей описываются в руководстве администратора. Реальные персональные данные использовать запрещено.

### Продакшен-сборка стенда (с этапа 2)

```bash
pnpm build                     # сборка обеих частей
pnpm --filter ./server start   # сервер раздаёт API (/api) и статику клиента
```

После запуска весь стенд доступен на одном порту сервера; глубокие ссылки вида `/clubs/robototehnika` работают благодаря возврату `index.html` для не-API маршрутов.

## Переменные окружения

Клиент (`client/.env.example`) — все значения публичны, секретов не содержат:

| Переменная          | Назначение        | По умолчанию |
| ------------------- | ----------------- | ------------ |
| `VITE_API_BASE_URL` | Базовый адрес API | `/api`       |
| `VITE_APP_NAME`     | Имя приложения    | `StudClubs`  |

Сервер (`server/.env`; состав по соглашению о разработке, `.env.example` появится вместе с каркасом сервера):

| Переменная         | Назначение                      | Пример                                                    |
| ------------------ | ------------------------------- | --------------------------------------------------------- |
| `NODE_ENV`         | Режим работы                    | `development`                                             |
| `PORT`             | Порт сервера                    | `3000`                                                    |
| `DATABASE_URL`     | Строка подключения к PostgreSQL | `postgresql://postgres:postgres@localhost:5432/studclubs` |
| `SESSION_SECRET`   | Ключ подписи средств доступа    | случайное значение                                        |
| `ACCESS_TOKEN_TTL` | Срок действия средства доступа  | `15m`                                                     |
| `CORS_ORIGIN`      | Разрешённый источник клиента    | `http://localhost:5173`                                   |
| `CLIENT_DIST_PATH` | Путь к собранному клиенту       | `../client/dist`                                          |
| `LOG_LEVEL`        | Уровень журналирования          | `info`                                                    |

## Роли пользователей

| Роль               | Основание                            | Область видимости                                               |
| ------------------ | ------------------------------------ | --------------------------------------------------------------- |
| Гость              | Без входа                            | Публичный каталог, только чтение                                |
| Обучающийся        | Запись в реестре, статус «обучается» | Свои заявки, участия, регистрации, профиль                      |
| Руководитель клуба | Действующее назначение               | Только закреплённый клуб + права студента, если сам обучающийся |
| Администратор      | Назначение на сотрудника             | Все данные, справочники, журнал, управление данными             |

Полный перечень прав по ролям приведён в техническом задании; проверка полномочий выполняется сервером при каждом обращении и не может быть обойдена клиентом.

## Порядок совместной разработки

Разграничение работ выполнено по частям Системы, а не по подсистемам: каждая функциональная подсистема реализуется в обеих частях. Клиентскую часть (`client/`) ведёт Евгений Доронин, серверную (`server/`) — Никита Сивцов; контракт, `shared/`, модель данных и правила — совместная зона, изменяемая только по взаимному согласию с записью в [журнале интеграции](docs/integration-log.md). Полный порядок — в [соглашении о разработке](docs/development-agreement.md).

Этапы интеграции:

| Этап | Содержание                                                                                                                            |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------- |
| 1    | Контракт версии 1.0.0, общий модуль, схема БД и начальная миграция, каркас сервера, операция проверки работоспособности `/api/health` |
| 2    | Раздача клиента сервером, вход и выход, роли и защита зон, демо-набор с учётными записями всех ролей                                  |
| 3    | Публичный каталог: поиск, фильтры, карточка клуба, похожие объединения и рекомендации                                                 |
| 4    | Заявки: подача, отзыв, рассмотрение, одобрение одной неделимой операцией, конфликты версий, просрочка                                 |
| 5    | Состав и администрирование: реестры, мастера, справочники, назначения, импорт CSV, массовый выпуск                                    |
| 6    | Аналитика, журнал аудита, резервные копии, сброс к демо-состоянию; приемочные сценарии и замеры                                       |
