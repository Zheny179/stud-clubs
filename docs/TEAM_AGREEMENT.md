## 1. Общие положения

Этот документ предназначен для разработчиков команды с целью соблюдения общих правил, обеспечения единообразия кода и процессов в проекте, а также для ускорения адаптации новых участников в процесс разработки системы.

### 1.1 Назначение и область действия

Настоящее соглашение устанавливает правила совместной разработки двух частей
Системы в общем репозитории: зоны ответственности, порядок работы с версиями,
соглашения об именовании и стилей кода, порядок изменения общих артефактов и точки
интеграции.

Соглашение не заменяет и не изменяет техническое задание (ТЗ): при возникновении
противоречий приоритет имеет ТЗ, а толкование спорных мест фиксируется в журнале
интеграции по взаимному согласию.

Документ отвечает на три вопроса:

- **кто за что отвечает** — раздел 2,
- **как выглядит сделанная работа** — раздел 3-6,
- **как договориться об изменении общего** — раздел 7.

Также в документе зафиксированы:

- Раздел 4-5 — конкретные значения, которых ТЗ не задаёт.
- Раздел 8-9 — точки интеграции и журнал.

**Требования ТЗ здесь не пересказываются.** Соглашение описывает только то, чего в ТЗ нет: правила совместной работы и принятые значения.

## 3. Управление работой и документацией

В этом разделе описаны правила планирования задач, отслеживания прогресса и ведения документации, чтобы все участники команды работали в едином информационном пространстве.

### 3.1 Ведение задач

Для планирования и координации работы используется встроенный трекер задач репозитория — [`GitHub Issues`](https://docs.github.com/en/issues)

Правила работы:

- Одна задача — одна конкретная цель (новая страница, эндпоинт API, исправление дефекта или предложение по изменению контракта).
- В заголовке кратко формулируем суть работы; каждой задаче назначается исполнитель (Assignee) и метка (Label) по типу и области.
- Крупные функции, найденные ошибки и любые изменения общих артефактов оформляются через Issue; мелкие локальные правки внутри своей части (например, корректировка отступов или рефакторинг одного файла) допускается вносить сразу через рабочую ветку и PR.
- В описании PR указывается ключевое слово со ссылкой на задачу (`Closes #<номер>`), чтобы она закрывалась автоматически после слияния в main.

Статусы задач и критерии готовности (Definition of Done):

| Статус              | Значение                                                                        |
| ------------------- | ------------------------------------------------------------------------------- |
| `Backlog` / `To Do` | Задача описана, согласована и ожидает начала работы                             |
| `In Progress`       | Исполнитель назначен, создана рабочая ветка, ведётся написание кода или тестов  |
| `In Review`         | Открыт PR в ветку main, ожидается проверка напарником                           |
| `Done`              | Получено одобрение (Approve), пройдены проверки, PR влит в main, задача закрыта |

Задача считается выполненной (Done), только если:

1. Код соответствует соглашениям стиля и проходит локальные проверки без ошибок.
2. Обновлена сопутствующая документация и контракт (если менялось поведение или API).
3. Pull Request проверен и одобрен вторым участником команды, а все замечания в комментариях закрыты.

### 3.2 Проектная документация

Вся техническая документация хранится в актуальном состоянии в папке [`/docs`](./) общего репозитория.

Структура и содержимое папки `/docs`:

- Соглашение о разработке (текущий документ) — общие правила команды, стандарты кода и зоны ответственности.
- Спецификации API и контракты — схемы взаимодействия между частями Системы (OpenAPI)
- Журнал интеграции, для фиксация спорных моментов из ТЗ.
- Инструкции по запуску и окружению — гайды по локальному развертыванию проекта, настройке зависимостей и переменным окружения

Правила ведения документации:

- Документация оформляется в формате Markdown (.md).
- Любое изменение архитектуры, API или точек интеграции должно сопровождаться обновлением соответствующих файлов в `/docs` в рамках того же PR.

## 4. Архитектура проекта

В проекте используется монорепозиторий (workspaces pnpm). Такой подход позволяет держать клиентскую, серверную части, общие типы и документацию в едином репозитории, упрощая синхронизацию изменений и контроль версий.

Базовая структура директорий:

```
studClubs/
├── client/
│   ├── src/
│   │   ├── app/
│   │   ├── components/
│   │   ├── api/
│   │   ├── stores/
│   │   ├── hooks/
│   │   ├── models/
│   │   ├── constants/
│   │   ├── utils/
│   │   ├── styles/
│   │   ├── assets/
│   │   └── main.tsx
│   ├── .env.example, .gitignore, eslint.config.js, stylelint.config.mjs
│   └── tsconfig*.json, vite.config.ts, index.html, README.md
├── server/
│   ├── src/
│   ├── tsconfig.json
│   ├── prisma/
│   ├── .env.example
│   └── README.md
├── shared/
│   └── src/
├── docs/
│   ├── openapi.json
│   ├── TEAM_AGREEMENT.md
│   ├── integration-log.md
│   ├── tz/
|   └── server/
├── pnpm-workspace.yaml, package.json, pnpm-lock.yaml
├── .editorconfig, .prettierignore, prettier.config.mjs, eslint.config.js
└── .gitignore, LICENSE, README.md
```

- Корневая директория (`/`) — содержит общие для всего проекта настройки линтеров, форматтеров и управление зависимостями.
- `client/` и `server/` — независимые приложения, которые имеют собственные конфигурации сборки, переменные окружения и инструкции по запуску.
- `shared/` — общая кодовая база, доступная обоим приложениям через зависимости workspace. Сюда выносятся структуры данных, перечисления и правила валидации, чтобы избежать дублирования кода.

## 5. Правила стиля кода

В проекте применяются единые стандарты оформления и написания кода для всех рабочих пространств (`client`, `server`, `shared`). Соблюдение этих правил контролируется автоматически с помощью линтеров и форматтеров.

### 5.1 Автоматизация и инструменты

- Форматирование (Prettier и .editorconfig): правила отступов, кавычек, точек с запятой и переносов строк задаются централизованно в корневых файлах prettier.config.mjs и .editorconfig. Код должен быть отформатирован перед созданием коммита.
- Статический анализ (ESLint и Stylelint): проверка качества TypeScript/JavaScript-кода выполняется через eslint.config.js, а стилей в клиентской части — через stylelint.config.mjs.

### 5.2 Соглашения об именовании

Единые правила именования сущностей, файлов и директорий позволяют легко ориентироваться в кодовой базе без необходимости открывать содержимое файлов.

| Сущность                                         | Стиль именования                  | Пример                                                | Примечание                                                                  |
| :----------------------------------------------- | :-------------------------------- | :---------------------------------------------------- | :-------------------------------------------------------------------------- |
| **Переменные, функции, методы**                  | `camelCase`                       | `getUserById`, `isAuthorized`                         | Булевы значения начинаются с `is`, `has`, `can`, `should`.                  |
| **Классы, типы, интерфейсы**                     | `PascalCase`                      | `ClubMember`, `AuthResponse`                          | Префикс `I` для интерфейсов не используется (`User`, а не `IUser`).         |
| **Перечисления (Enum) и их ключи**               | `PascalCase` / `UPPER_SNAKE_CASE` | `enum UserRole { ADMIN = 'ADMIN' }`                   | Имя перечисления в `PascalCase`, значения — в `UPPER_SNAKE_CASE`.           |
| **Глобальные константы**                         | `UPPER_SNAKE_CASE`                | `MAX_FILE_SIZE`, `API_BASE_URL`                       | Только для неизменяемых конфигурационных значений.                          |
| **Файлы React-компонентов**                      | `PascalCase.tsx`                  | `ClubCard.tsx`, `Header.tsx`                          | Имя файла должно совпадать с именем экспортируемого компонента.             |
| **Прочие файлы (хуки, сервисы, утилиты, стили)** | `kebab-case`                      | `use-auth.ts`, `club.service.ts`, `layout.module.css` | Для серверных слоев допускается суффикс роли (`.controller.ts`, `.dto.ts`). |
| **Директории**                                   | `kebab-case`                      | `user-profile/`, `auth-forms/`                        | Строго нижний регистр, без пробелов и спецсимволов.                         |

### 5.3 Общие принципы написания кода

Чтобы код было легко читать, поддерживать и дорабатывать всей команде, придерживаемся нескольких базовых правил:

- Строгая типизация: использование типа any запрещено. При работе с неизвестными внешними данными применяется unknown с последующей валидацией
- Модульность и импорты: для импорта из пакета shared используются настроенные алиасы путей (например, `@studclubs/shared`), а не относительные пути вида `../../../shared`.

## 6. Работа с git

В проекте используется единый подход к ведению истории изменений, ветвлению и слиянию кода. Это помогает легко ориентироваться в логах репозитория, безопасно выпускать обновления и быстро находить причину багов.

### 6.1 работа с комитами

Мы придерживаемся стандарта **Conventional Commits**.

Каждый коммит оформляется по шаблону: `тип(область): краткое описание`.

| Тип        | Назначение                         |
| ---------- | ---------------------------------- |
| `feat`     | новая функция                      |
| `fix`      | исправление дефекта                |
| `refactor` | перестройка без смены поведения    |
| `docs`     | документация                       |
| `chore`    | обслуживание, конфиги, зависимости |
| `test`     | испытания                          |

Области: `client`, `server`, `shared`, `contract`, `docs`, `repo`.

Требования к коммитам:

- Описание пишется на русском языке с маленькой буквы, без точки в конце, длиной до 72 символов.
- Используем повелительное наклонение или формулировку «что сделано»
- Один коммит — одно логическое изменение: не смешиваем рефакторинг, фикс бага и новую фичу в одном коммите.

Примеры:

```
feat(client): добавить форму подачи заявки
fix(server): проверить свободные места при одобрении в транзакции
docs(contract): описать операция отзыва заявки (версия 1.1.0)
```

**Указание соавторов (`Co-authored-by`):**
Если задача выполнялась совместно (парное программирование, совместная проработка контракта или доработка чужого PR), в самом конце сообщения коммита (через пустую строку от основного текста) добавляется трейлер `Co-authored-by`:

```text
docs(contract): описать операцию отзыва заявки (версия 1.1.0)

Co-authored-by: Nik-git-C <Nik-git-C@users.noreply.github.com>
```

### 6.2 работа с ветками

В репозитории есть только одна долговременная ветка — `main`. Она всегда должна собираться, проходить все проверки и оставаться в рабочем состоянии.

> Она защищена набором правил GitHub (Ruleset protect-main) без исключений.

Все задачи разрабатываются в отдельных короткоживущих ветках, созданных от актуального `main`

Формат названия ветки: `тип/краткое-описание-на-английском` (в `kebab-case`)

Пример:

- `feat/application-form`
- `fix/duplicate-membership`
- `refactor/header-animation`
- `docs/agreement-v2`
- `chore/quality-gates`
- `test/shared-automata`

### 6.3 работа с Pull request

Слияние любой ветки в `main` происходит исключительно через PR после проверки другим участником команды.

Правила создания, ревью и слияния PR:

- В теле PR указываем, какая задача решена, что именно изменилось и как это можно проверить (при изменениях интерфейса прикладываем скриншоты или видео)
- Стараемся делать PR компактными (одна задача — один PR)
- Перед запросом ревью убеждаемся, что проект собирается, тесты проходят, а линтеры не выдают ошибок. В репозитории активирована проверка статусов (**Require status checks to pass**), поэтому при добавлении обязательных CI-проверок их успешное прохождение требуется для слияния.
- Для влития требуется минимум 1 апрув (Approve) от другого разработчика. Если после одобрения в ветку отправляются новые коммиты, прежние апрувы автоматически сбрасываются и ревью нужно пройти повторно.
- Все ветки комментариев и замечания ревьюеров должны быть разрешены (**Resolve conversation**) до слияния.
- Влитие в `main` выполняется только стандартным методом Merge (другие стратегии отключены). После успешного слияния рабочую ветку необходимо удалить.

## 7 Порядок пересмотра и обновления

В этом разделе описаны правила внесения изменений в контракты, код и документацию, а также регламент поддержания настоящего соглашения в актуальном состоянии.

### 7.1 Порядок пересмотра (изменение контрактов и правил)

Используется при изменении API-контрактов, общих моделей данных (`shared/`), структуры БД или пунктов настоящего соглашения.

1. Инициатива. Инициатор оформляет письменное предложение (фиксация в `Issue` репозитория), где указывает:

   - что и зачем меняется;
   - какие операции, типы данных или таблицы затронуты;
   - является ли изменение ломающим (breaking change).

2. Согласование. До начала разработки, второй участник команды изучает предложение и явно подтверждает согласие на изменения (отметкой в журнале или комментарием в `Issue`). Молчание согласием не считается.

3. Версионирование. При изменении спецификации API (`openapi.yaml`) или настоящего соглашения обновляется версия по стандарту `SemVer` (MAJOR.MINOR.PATCH):
   - MAJOR — ломающие изменения (удаление полей, изменение типов, смена логики эндпоинтов);
   - MINOR — обратная совместимость сохранена (добавление новых эндпоинтов или опциональных полей);
   - PATCH — исправление опечаток в документации или багов без изменения структуры контракта.

4. Реализация. Контракт, директория `shared/`, серверная и клиентская части обновляются согласованным комплектом PR в рамках ближайшего окна интеграции. Ломающее изменение не вливается одной стороной раньше, чем другая готова его принять; порядок слияния клиентского и серверного PR согласуется заранее.

5. Фиксация. После слияния PR в журнал изменений вносится итоговая запись по шаблону: список затронутых артефактов, отметки о согласовании обоих участников и ссылки на закрытые PR.

### 7.2 Порядок обновления (процесс разработки)

Используется для повседневной работы над задачами в рамках согласованных контрактов.

Базовый цикл работы с кодом:

1. Постановка и согласование. Создание задачи и получение предварительного согласия (одобрения на реализацию и последующее создание PR) от второго участника или владельца затронутой зоны.
2. Создание ветки. Ответвление от актуального `main` (например, `feat/task-name` или `fix/bug-name`).
3. Разработка. Написание кода, тестов и обновление сопутствующей документации.
4. Фиксация изменений. Оформление атомарных, понятных коммитов в рабочей ветке.
5. PR и слияние. Открытие PR, прохождение ревью, вливание изменений в `main` и удаление рабочей ветки.

Обязательные правила:

- Границы зон ответственности. Прямые коммиты в чужую кодовую базу без предварительного согласования, PR и ревью её владельца запрещены.
- Разделение кросс-платформенных задач. Задача, затрагивающая и backend, и frontend, разбивается на два отдельных PR (серверный и клиентский), которые согласуются и вливаются в одном окне интеграции.
- Ответственность за проверки. Каждый владелец отвечает за работоспособность своей зоны. Если изменения автора «ломают» проверки в чужой зоне, слияние PR блокируется до устранения проблемы.
- Критерий завершенности (DoD). Актуальные README.md, .env.example и тесты для своей части кода — обязательная зона ответственности владельца. Без них задача не считается выполненной.

> Не править чужой код. Порядок: Описание задачи → согласование контракта (раздел ) → работа против заглушки по контракту с пометкой `// TODO: подключить реальную операцию`.

**Заглушка не считается реализацией требования** и не даёт права отмечать пункт готовым.

## 8. Точки интеграции

Суть: точка — это состояние, а не дата.
Точка интеграции считается достигнутой, когда сквозной сценарий проходит, а не когда «оба влили свои ветки». Слияние PR — необходимое условие, но не сама точка.
Отсюда два следствия:

1. точку нельзя назначить на пятницу — она наступает по готовности проекта;
2. точку нельзя отметить в одиночку — «у меня локально работает» не критерий.

## 9. Журнал интеграции

Журнал ведётся в [`docs/integration-log.md`](/docs/integration-log.md) и является обязательным артефактом приемки. Запись вносится при каждом: согласовании или изменении общего артефакта; достижении точки интеграции; разрешении спорного вопроса; согласовании толкования ТЗ; изменении настоящего соглашения; инциденте с секретом или данными.

Обязательные поля: порядковый номер, дата, вид события, инициатор, суть, версия контракта «было → стало» (если применимо), затронутые артефакты, решение и результат проверки (сценарии, замеры, отказы сервера), отметки обоих исполнителей с датами, ссылки на PR/коммит/тег.

Нумерация сквозная и возрастающая. Записи не редактируются задним числом: исправление оформляется новой записью со ссылкой на исправляемую.
